# Measurements — Phase 8 web UI (2026-09-21)

Measured, not claimed. Phase 8 adds no Rust hot path worth a criterion bench: what it adds is a browser, so what is measured here is what a browser does with a realistically large library. The numbers are a baseline for regressions, not a performance guarantee. Nothing here touches a remote host.

## Setup

| Item | Value |
|---|---|
| Machine | 4 vCPU Intel Xeon @ 2.80 GHz, 16 GB RAM (shared cloud container, no CPU pinning) |
| Server | `uguisu serve` from the **debug** binary — a release build is faster, so every server-side figure below is pessimistic |
| Browser | Chromium 1194 (the container's Playwright build), headless, 1280×900, no CPU or network throttling |
| UI | `pnpm --dir web build`, served by `uguisu serve --web web/dist` over loopback |
| Publisher | a local Python HTTP server standing in for the feeds and enclosures |
| Method | 5 timed runs after one discarded warm-up, on a fresh page each time; medians and ranges reported |

Two fixtures, both seeded through the public API:

| Fixture | Contents |
|---|---|
| **large** | 120 podcasts; 5 428 episodes indexed, 4 000 of them on one show |
| **slow** | 6 podcasts × 8 episodes of 6 MiB, served at roughly 2 MiB/s per connection so the download progress meter has something to report |

Timings start at the navigation and end when the assertion a person would make becomes true — a count painted, a row rendered, results visible — not at `load`, which for this UI never fires while the event stream is open.

## Bundle

| Artifact | Bytes | gzip |
|---|---|---|
| `index-*.js` | 136 244 | 42 440 |
| `index-*.css` | 14 573 | 3 546 |
| `index.html` | 448 | 279 |
| **total** | **151 265** | **46 265** |

One request for each, both content-hashed and served `immutable`. Zero runtime dependencies: everything in that bundle is Uguisu's own code plus Svelte's runtime.

## Pages, on the large fixture

| What | Median | Range |
|---|---|---|
| dashboard: open → the library count painted | 262 ms | 255–272 |
| library: open → a named row among 120 painted | 268 ms | 261–276 |
| library: filter keystroke → filtered list | 20 ms | 18–24 |
| podcast detail: open → the first episode page (50 of 4 000) | 137 ms | 134–145 |
| episodes: nine more pages, to 500 rows | 1 461 ms | 1 395–1 507 |
| local search: keystroke → results painted | 810 ms | 806–817 |
| queue: open → heading painted | 72 ms | 67–78 |
| archive: open → heading painted | 76 ms | 73–81 |
| settings: open → a key painted | 113 ms | 106–123 |
| player: click → the audio element mounted with its source | 104 ms | 85–112 |

**The dashboard's 262 ms is `/api/v1/status`, not rendering.** That endpoint makes four engine calls and one of them lists every podcast with a per-podcast detail query, so it grows with the library. The UI paints as soon as it answers.

**The library's 268 ms is one response containing 120 podcasts** with their sources and counts. Filtering that list afterwards costs 20 ms including the keystroke, the URL replacement and the re-render — which is why the browser-side filter is an acceptable trade for now, and why the fix when it stops being acceptable is a paginated endpoint rather than a cleverer filter.

**Episode paging is 9 sequential round trips**, about 162 ms each, because "load more" is a cursor request and the next one cannot start until the first returns. A person clicking through pages perceives each one, not the total.

**Search's 810 ms includes the 250 ms the UI deliberately waits** before sending anything, so the server and render together are about 560 ms for a two-term query over 5 428 indexed episodes on the debug build. `search/reindex` for that library took 4.9 s.

**The player's 104 ms is the UI's cost** — the element mounted with its `src`. What happens after that is the browser's media pipeline and the range request it makes, which `scripts/e2e.py` asserts separately (200 with the full length, 206 with an exact `Content-Range`, 304 on a matching validator). Audible playback was confirmed interactively in Chromium; it is not timed here, because a headless container has no audio device and any number would be measuring the environment.

## The queue under live progress

On the **slow** fixture: every podcast enqueued, then ten seconds of `requestAnimationFrame` sampling on the download queue.

| What | Value |
|---|---|
| `download.progress` events received | 80 in 10.0 s (8/s) |
| rows on screen | 48 |
| live progress bars | 48 |
| frame interval, median | 16.7 ms |
| frame interval, p95 | 16.7 ms |
| frame interval, worst | 33.3 ms |

A steady 60 fps with one dropped frame in ten seconds, while every visible bar is being updated from the stream.

Eight events per second is what Uguisu actually produces, and the ceiling is arithmetic rather than a guess: one event per running job per `UGUISU_DOWNLOAD_PROGRESS_INTERVAL_MS`, so the default `UGUISU_DOWNLOAD_GLOBAL_CONCURRENCY=3` at the default 1 000 ms interval is 3/s, and this run's 100 ms interval with three or four jobs in flight is the 8/s observed. The rate does not grow with the size of the queue — only with how many jobs are downloading at once — so the measured figure is close to the worst case, not a fraction of it.

## A thousand episode rows

| Rows on screen | DOM elements | JS heap |
|---|---|---|
| 50 (one page) | 618 | 10 MiB |
| 1 000 (twenty pages) | 10 118 | 10 MiB |

About **9.5 DOM elements per episode row**, and the heap does not move: the rows are plain markup, not component instances holding state. Twenty pages is past what anyone loads by hand, and it stays interactive, which is why Phase 8 ships cursor paging instead of virtualization. The point where virtualization earns its complexity is somewhere above this, and the measurement above is the baseline to compare against when someone claims it has arrived.

## What is not measured here

- **A release build.** Every server-side number above is from `target/debug`. The shape — which figures grow with the library and which do not — is the part worth reading.
- **Cold browser cache versus warm.** Each run navigates a fresh page in the same browser, so the bundle is parsed from Chromium's cache. A first visit adds one 46 KB transfer.
- **A 10 000-podcast library.** The `/api/v1/podcasts` response is the binding constraint long before rendering is, and it is a backend shape, not a UI one; `docs/WEB_UI.md` records it as a known limitation.
- **An event rate far above what Uguisu emits.** Progress events are bounded by running jobs ÷ interval, so there is no realistic configuration that produces hundreds per second. Raising the rate artificially would measure Svelte, not Uguisu.
- **Lighthouse and visual regression.** Deferred with the rest of the browser-automation tooling (`docs/ROADMAP.md` § Phase 8).
