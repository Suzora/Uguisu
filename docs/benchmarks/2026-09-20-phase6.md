# Benchmarks — Phase 6 archive portability and metadata (2026-09-20)

Measured, not claimed. The numbers come from two criterion runs and one end-to-end run with the release binary on the development container. They are a baseline for regressions, not a performance guarantee. Nothing here touches a remote host: the feed, the media and the artwork of the end-to-end run are served from loopback.

Phase 6's cost is almost entirely **per document and per file**, not per byte. A sidecar is written once per episode, a manifest once per podcast per batch, a tag once per explicit command. The one place where bytes still dominate is copying and hashing during an import, and that is bounded by SHA-256 exactly as Phase 5's `verify --full` is.

## Setup

| Item | Value |
|---|---|
| Machine | 4 vCPU Intel Xeon @ 2.10 GHz, 16 GB RAM (shared cloud container, no CPU pinning) |
| Toolchain | rustc 1.94.1, release profile, `cargo bench` |
| Criterion settings | `--warm-up-time 1 --measurement-time 3 --sample-size 20` |
| Benches | `crates/uguisu-archive/benches/archive.rs`, `crates/uguisu-metadata/benches/tags.rs` |
| Storage | temporary directories on the container's overlay filesystem |

Reproduce with:

```bash
cargo bench -p uguisu-archive  --bench archive -- --warm-up-time 1 --measurement-time 3 --sample-size 20
cargo bench -p uguisu-metadata --bench tags    -- --warm-up-time 1 --measurement-time 3 --sample-size 20
```

## Sidecars

One document per archived file, written once and read only by a rebuild.

| Operation | Time |
|---|---|
| render a sidecar (pretty JSON, stable key order) | 2.83 µs [2.81, 2.85] |
| parse one back | 5.92 µs [5.85, 5.97] |

Parsing costs twice rendering because it validates: the schema version is probed before the document is deserialized, so a sidecar from a future version is refused by name rather than by a type error halfway through. At 5.9 µs a rebuild of a 10 000-episode archive spends **59 ms parsing** — the scan around it is the cost, not the JSON.

## Manifests

One line per archived episode, rendered from the database and never from a filesystem walk.

| Operation | 1 000 entries | 10 000 entries |
|---|---|---|
| render | 268 µs | 2.62 ms |
| parse | 547 µs | 5.81 ms |
| compare against what is on disk | 344 µs | 4.17 ms |

All three are linear in entries — 10× the input costs 9.8×, 10.6× and 12.1× the time — which is what the streaming writer and the `BTreeMap` comparison are for. A 10 000-episode podcast's manifest is rendered in under three milliseconds, so the reason manifests are written in batches is not CPU: it is the two fsyncs that make the write atomic, and the rule that a finished download must never wait on derived data.

`compare` is cheaper than `parse` because it never allocates a string per line.

## Scanning a tree

1 000 files in 10 directories, the input a rebuild or an import starts from:

| Operation | Time | Per file |
|---|---|---|
| walk with a 16-byte head read | 3.41 ms | 3.4 µs |
| walk with sizes only | 1.87 ms | 1.9 µs |

Reading the first sixteen bytes of every file — which is what lets the scanner tell media from a stray text file without trusting the extension — costs **1.5 µs per file**, or 15 ms per 10 000 files. That is cheap enough that it is the default.

The scan streams: memory is one directory entry at a time, not one vector of a million paths. A 100 000-file import tree is therefore a 340 ms scan and a few kilobytes of peak memory, not a 100 000-element allocation.

## Matching one file against a podcast

The inner loop of an import: one candidate scored against every episode of one show.

| Operation | Time | Per episode |
|---|---|---|
| classify against 1 000 episodes | 3.64 ms | 3.6 µs |

Scoring normalizes both titles (NFKC, case folding, transliteration) and runs Jaro-Winkler over them, which is where the time goes. It is linear in episodes, so importing a 500-file tree into a 1 000-episode show is about **1.8 s of scoring** — noticeable, and worth knowing before someone imports a decade of a daily show. It is also exactly once per file: the plan is computed once and the apply pass re-uses it.

## Artwork

| Operation | Time |
|---|---|
| validate a 512 KiB PNG (declared type + signature) | 47.7 ns |

Validation reads twelve bytes. The size in the name is there to show that it does **not** scale with it: Uguisu does not decode the image, which is why the `image` crate was not adopted (ADR 0026). The cost of artwork is the network fetch and the hash, not the check.

## Tags

Thirteen managed fields written into a file that has none, then read back, then written again when everything already agrees. The write case includes re-creating the file from scratch, because the engine never tags an original in place — it tags a copy.

| Operation | MP3 (ID3v2) | FLAC (Vorbis comments) |
|---|---|---|
| read the managed fields | 16.9 µs | 7.00 µs |
| write them into an untagged file (incl. the copy) | 623 µs | 195 µs |
| write when nothing needs changing | 18.3 µs | 7.01 µs |

The last row is the one that matters most, and it is not a micro-optimization: a second `sync` write **opens nothing for writing**, so the file's bytes — and therefore the archive's hash, the sidecar and the manifest — do not move. A field that failed to round-trip would turn every run into a rewrite of the whole archive; four such fields were found by the guard test and removed from the managed set rather than shipped (ADR 0026).

ID3v2 is 2–3× the cost of Vorbis comments in every row: frames are length-prefixed and the tag is rewritten at the head of the file, while a FLAC metadata block is replaced in place.

## End to end with the release binary

`target/release/uguisu` against a loopback HTTP host serving two feeds (three and five episodes, ~1 MiB enclosures) and a PNG, on a temporary data directory. Wall time is the whole process — start, engine open, migrations, the command, close — which is why nothing here is under 13 ms. CPU is user+system of that process; RSS is the high-water mark across all child processes of the run.

| Step | Wall | CPU | Peak RSS |
|---|---|---|---|
| `podcast add` (resolve, fetch, ingest 3 episodes) | 1.68 s | 68 ms | 21.6 MiB |
| `download podcast` (queue 3) | 22 ms | 21 ms | 22.2 MiB |
| `download run --until-idle` (3 MiB) | 45 ms | 47 ms | 22.2 MiB |
| `archive manifest status` | 14 ms | 15 ms | 22.2 MiB |
| `archive manifest write` | 13 ms | 14 ms | 22.2 MiB |
| `archive manifest verify --full` | 18 ms | 19 ms | 22.2 MiB |
| `archive tags write --mode sync` | 28 ms | 25 ms | 23.5 MiB |
| `archive tags write` again (no-op) | 20 ms | 21 ms | 23.8 MiB |
| `archive reconcile --rebuild` (dry run, 3 sidecars) | 17 ms | 18 ms | 23.8 MiB |
| `archive reconcile --rebuild --apply` | 19 ms | 20 ms | 23.8 MiB |
| `archive verify --podcast --full` after the rebuild | 20 ms | 21 ms | 23.8 MiB |
| `archive import` (dry run, 4 candidates) | 18 ms | 19 ms | 23.9 MiB |
| `archive import --apply` (copies 2) | 31 ms | 29 ms | 23.9 MiB |
| `archive import --apply` again | 21 ms | 22 ms | 23.9 MiB |
| `archive artwork fetch` | 17 ms | 17 ms | 23.9 MiB |
| `archive artwork fetch` again (conditional) | 16 ms | 16 ms | 23.9 MiB |

`podcast add` is a second and a half of *network*: feed resolution, the first conditional fetch, parsing and the first refresh. Everything else in Phase 6 is tens of milliseconds, most of it process start and engine open — the work itself is the few hundred microseconds the sections above measure.

**Peak RSS never exceeds 24 MiB** across the whole run, including the import that copies and hashes files and the tag write that rewrites one. Nothing in Phase 6 loads a file, a tree or a manifest into memory whole.

One measurement was an outlier worth naming rather than smoothing away: a second `archive manifest write` in the first run took 216 ms where every other manifest write took 13–28 ms. It did not reproduce — three repeats of a genuinely stale write on the same data measured 26, 27 and 28 ms, and three no-op writes 25, 27 and 34 ms — so it was container I/O, not a code path. It is recorded here because a benchmark that only reports the runs that behaved is not a measurement.

### What the run asserted, not just timed

The end-to-end script checks behaviour at every step; the numbers above are a by-product. What it proved:

| Assertion | Result |
|---|---|
| layout | `Die Pizza-Akte/2024/2024-01-15 - Folge 141- Käse & Ketchup — Teil 1.mp3` |
| a sidecar beside every archived file | 3 of 3 |
| the manifest was already current after the queue went idle | yes — `stale: false`, written without being asked |
| every manifest digest matches the file on disk | yes (re-hashed outside Uguisu, in the script) |
| `sha256sum -c` format | header comments plus `<64 hex><2 spaces><relative path>` |
| tag write moved `hash_value` | yes |
| the new `hash_value` matches the bytes on disk | yes |
| `source_hash_value` unchanged, and equal to the download's hash | yes |
| the sidecar agrees with the file after tagging | yes |
| the manifest was marked stale by the tag write | yes |
| a second `sync` write | `nothing_to_write`, file byte-identical |
| deleting 3 `archive_files` rows, then a dry-run rebuild | 3 scanned, 3 would be rebuilt, **0 rows written** |
| `--apply` | 3 rebuilt, all `unchecked`, reason `rebuilt`, origin `rebuild` |
| the rebuilt record of the tagged file | carries the tagged hash *and* the original `source_hash_value`, from the sidecar alone |
| `verify --full` after the rebuild | 3 verified |
| rebuilding again | 3 unchanged, 0 rebuilt |
| import dry run | 2 importable (confidence 97), 2 refused; **nothing written** |
| import apply | 2 imported, 2 refused, source tree **byte-identical before and after** |
| the ambiguous file (`Das Interview.mp3`, two episodes at 100) | not imported — "two episodes explain the file equally well" |
| the unmatched file (confidence 64) | not imported — "no episode explains the file well enough" |
| importing the same tree again | 2 `already_present`, 0 imported, nothing overwritten |
| importing the media directory into itself | refused, exit 1, `import_source_invalid` |
| artwork | fetched, stored at `.uguisu/artwork/<podcast-id>/<sha256>.png`, bytes match the hash in its name |
| artwork again | `unchanged` — a conditional request, no second copy |
| database after all of it | 316 KiB for 8 episodes, 5 archived files, 1 image |
