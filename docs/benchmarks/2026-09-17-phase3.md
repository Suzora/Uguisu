# Benchmarks — Phase 3 feed engine (2026-09-17)

Measured, not claimed. Numbers come from one criterion run and one manual measurement on the development container; they are a baseline for regressions, not a performance guarantee.

## Setup

| Item | Value |
|---|---|
| Machine | 4 vCPU Intel Xeon @ 2.80 GHz (shared cloud container, no CPU pinning) |
| Toolchain | rustc 1.94.1, release profile, `cargo bench` |
| Criterion settings | parser: `--warm-up-time 1 --measurement-time 3 --sample-size 20`; refresh: `--warm-up-time 1 --measurement-time 5 --sample-size 10` |
| Benches | `crates/uguisu-feed/benches/parser.rs`, `crates/uguisu-engine/benches/refresh.rs` |
| Network | none; the refresh benches fetch from an in-process wiremock server on loopback |
| Database | temporary directory, SQLite WAL, `synchronous=NORMAL` (ADR 0002) |

Reproduce with:

```bash
cargo bench -p uguisu-feed --bench parser -- --warm-up-time 1 --measurement-time 3 --sample-size 20
cargo bench -p uguisu-engine --bench refresh -- --warm-up-time 1 --measurement-time 5 --sample-size 10
```

## Parser, normalizer and identity (`uguisu-feed`)

Synthetic RSS 2.0 feeds with GUIDs, RFC 2822 dates, CDATA show notes, `content:encoded`, iTunes and Podcasting 2.0 tags and one enclosure per item (≈ 810 bytes per item). Times are the criterion point estimate with the 95 % confidence interval.

| Items | `parse` (bytes → `ParsedFeed`) | `normalize` (channel + every item) | `identity` (signals, cascade, comparable hash) |
|---|---|---|---|
| 10 | 103.0 µs [102.7, 103.3] | 80.2 µs [79.9, 80.7] | 77.1 µs [77.0, 77.3] |
| 200 | 1.81 ms [1.80, 1.81] | 1.65 ms [1.64, 1.66] | 1.65 ms [1.63, 1.67] |
| 1 000 | 9.27 ms [9.20, 9.35] | 9.03 ms [8.79, 9.35] | 9.19 ms [9.03, 9.40] |
| 10 000 | 107.4 ms [106.1, 108.7] | 106.2 ms [105.6, 106.9] | 108.9 ms [108.4, 109.5] |

Throughput: the parser sustains ≈ 73–86 MiB/s; normalization ≈ 94–125 k items/s; identity ≈ 92–130 k items/s. All three stages are linear in the number of items (10 000 items ≈ 10 × 1 000 items), so the whole in-memory pipeline for a 10 000-item feed costs ≈ 320 ms of CPU.

## Refresh pipeline (`uguisu-engine`)

One podcast on a temporary database; every iteration is a full `Engine::refresh_podcast` including the HTTP round trip to the loopback mock, sniffing, fingerprinting, parsing, planning and the transaction.

| Benchmark | What is measured | 1 000 items | 10 000 items |
|---|---|---|---|
| `cold_import` | `add_podcast`: resolve (probe), insert, first refresh with every item new | 2.07 s [2.03, 2.11] | 5.67 s [5.53, 5.80] |
| `identical_fingerprint` | conditional refresh; host ignores validators; body hash equals the stored fingerprint → no parse | 4.16 ms [4.09, 4.24] | 25.8 ms [25.2, 26.6] |
| `identical_forced_full_parse` | `--force`: fetch, parse, plan, every episode unchanged (`mark_seen` in batches) | 75.9 ms [73.7, 77.4] | 643 ms [627, 657] |
| `one_added_or_missing` | alternate between *n* and *n + 1* items: one insert, or one missing streak | 74.6 ms [73.5, 76.4] | 659 ms [635, 682] |
| `one_updated` | alternate one changed title: one upsert plus change-log rows | 77.9 ms [75.4, 79.3] | 647 ms [629, 664] |

Observations:

- A refresh whose body did not change costs the HTTP round trip plus one SHA-256 of the body (≈ 4 ms for 800 KB, ≈ 26 ms for 8 MB) and one small transaction; an HTTP 304 is cheaper still.
- A full parse of an unchanged 10 000-item feed is ≈ 640 ms, half of it the in-memory pipeline (≈ 320 ms) and half loading the identity index and marking 10 000 rows seen in chunks of 500.
- Small deltas cost the same as an unchanged full parse: the planner is O(n) in hash maps, and the write set is one or two rows.
- The cold import is dominated by 10 000 individual `INSERT`s for episodes plus their enclosures inside one transaction (≈ 2.9 s of the 5.7 s for 10 000 items; the rest is the resolver's probe of a 4 MB body and the HTTP transfers). Multi-row inserts are the obvious next optimization if imports of very large archives matter (`docs/ROADMAP.md`).

## Memory and wall time of the release binary

Manual run of `target/release/uguisu` against a local `python3 -m http.server` serving a generated 10 000-item feed (4.06 MB); peak resident set size from `getrusage(RUSAGE_CHILDREN)`.

| Command | Wall time | Reported `duration_ms` | Peak RSS |
|---|---|---|---|
| `feed inspect <10k feed>` | 0.25 s | 224 ms | 67.6 MiB |
| `podcast add <10k feed>` (resolve + import) | 5.55 s | 2 865 ms (refresh only) | 100.7 MiB |
| `podcast refresh <id>` (HTTP 304 from the host) | 0.04 s | 4 ms | — |
| `podcast refresh <id> --force` (full parse, 10 000 unchanged) | 0.83 s | 724 ms | ≤ 100.7 MiB |

The database after the import is 18.3 MiB for 10 000 episodes with enclosures, extras and the change log. Peak memory stays around 100 MiB for the largest feed the limits allow by default items-wise; the body cap (`UGUISU_FEED_MAX_BYTES`, 50 MiB) bounds the parser's input.

## Test-suite timing

`cargo test -p uguisu-engine --test removal` includes a 10 000-item import, a fingerprint hit, a forced identical refresh and a +1/updated refresh through the engine; it finishes in ≈ 22 s in the debug profile on this machine.
