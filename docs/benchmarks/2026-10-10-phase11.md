# Benchmarks — Phase 11 scale: 10 000 feeds, 500 000 episodes, 100 000 archived files (2026-10-10)

Measured, not claimed. Uguisu was driven from outside, as a user drives it: the release `uguisu` binary and `uguisu serve`, against a publisher on the same machine, by `scripts/bench_scale.py`. The numbers describe one Windows desktop; they are a baseline, not a guarantee.

The run found five things worth changing, and four were changed before the numbers below were taken again (§ Findings). What stays above a target is named.

## Setup

| Item | Value |
|---|---|
| Machine | AMD Ryzen 9 9950X3D, 8 logical processors visible to Windows, 125 GB RAM |
| Disk | Samsung SSD 9100 PRO (NVMe), NTFS, Windows Defender real-time scanning on |
| OS | Windows 11 Pro 10.0.26300 |
| Build | release profile, rustc 1.98.1, at `4947415` |
| Network | none: a Python `ThreadingHTTPServer` on `127.0.0.1` serves every feed and enclosure |
| Settings | the defaults, but what a local publisher needs (`UGUISU_HTTP_ALLOW_PRIVATE_HOSTS=127.0.0.1`, Apple off, no free-space floor, no artwork fetch) and download concurrency 16 overall and per host |

Reproduce with:

```bash
python3 scripts/bench_scale.py --quick    # 100 feeds, 1 000 files, every assertion
python3 scripts/bench_scale.py            # the tiers below, about an hour
```

The script writes every step to `target/bench-scale/<mode>.json` and asserts what any run must show: the episode counts, a refresh of unchanged feeds that fetches nothing, one new episode per feed, a byte flip that only a full verification finds, a sound database and no orphans.

**How the API was timed.** Each series is 25 requests over one kept-alive connection, as a browser holds it. A new connection per request measured the client instead: on Windows, Python's socket timeouts cost a timer tick of about 15 ms now and then.

**What the targets are.** [`DATA_MODEL.md`](../DATA_MODEL.md) §7 sets list and filter queries under 50 ms at 10 000 podcasts and 500 000 episodes. ROADMAP adds two conditions that this run decides: multi-row inserts and virtualized lists only if this benchmark needs them.

## Feeds: 100, 1 000 and 10 000 podcasts of 50 episodes

Each feed is a separate show, served from one host and closing its connection, as separate hosts would. `podcast import --apply` resolves each feed once; `podcast refresh --all` runs at the default concurrency of 8.

| Step | 100 | 1 000 | 10 000 |
|---|---|---|---|
| `podcast import --apply` | 0.77 s | 3.67 s | 21.35 s, peak 108 MiB |
| `podcast refresh --all`, first (5 000 / 50 000 / 500 000 episodes) | 1.33 s | 16.44 s | 125.09 s, peak 159 MiB, 185 s CPU |
| the same, nothing changed (304) | 0.33 s | 1.15 s | 10.09 s |
| the same, one new episode in every feed | 0.47 s | 2.82 s | 27.04 s |
| `db check` | 0.27 s | 0.67 s | 4.97 s |
| `db backup` | 0.27 s | 0.50 s | 8.97 s |
| `db vacuum` | 0.60 s | 0.72 s | 8.73 s |
| `scheduler maintenance` | 0.26 s | 0.29 s | 1.97 s |
| `search reindex` | 0.48 s | 1.06 s | 11.62 s |
| database after the run | 12.8 MiB | 125.6 MiB | 1 137 MiB |
| `serve` until it answers | 0.53 s | 0.52 s | 0.53 s |

The first refresh costs between 0.25 and 0.33 ms per episode at every size: it grows with the episodes and no faster. The database holds about 2.3 KB per episode, the search index included.

**Verdict on multi-row inserts:** not needed. Importing 500 000 episodes takes two minutes once, and every later refresh touches only what changed.

Median and p95 of 25 requests each; a page is 50 rows unless it says otherwise.

| Request | Median | p95 |
|---|---|---|

| `/podcasts`, every page of 500, 20 pages | 34.49 ms | 35.94 ms |
| `/podcasts/{id}` | 0.42 ms | 0.61 ms |
| `/podcasts/{id}/episodes` | 1.21 ms | 1.49 ms |
| `/episodes/{id}` | 0.31 ms | 0.46 ms |
| `/search?kind=episodes`, one show's number | 9.63 ms | 10.68 ms |

Everything the UI lists stays under 50 ms, a page of 500 rows included. The one request above it is a search for a word in every one of 500 000 episodes: FTS5 ranks every match before it returns the best 50. A search for something that narrows it, here one show's number, takes 10 ms. This is accepted rather than changed.

**Verdict on virtualized lists:** not needed. The UI pages at 50 rows, and a page of 500 still arrives in 35 ms.

## Archive: 100 000 files

2 000 feeds of 50 episodes each, every episode downloaded through `serve` (a 52-byte WAV, so the cost per file is Uguisu's own, not the bytes'). Enclosures keep their connection, as one CDN serves a show's episodes.

| Step | Time |
|---|---|
| download and archive 100 000 files | 1 992 s, about 50 files a second; `serve` used 2 167 s CPU and peaked at 49 MiB |
| database after the downloads | 692 MiB |
| `archive verify --all` (light) | 36.02 s |
| the same after one file's last byte was flipped and its mtime put back | 23.82 s, nothing found, as designed |
| `archive verify --all --full` | 40.27 s, the flipped file found, the only one |
| `archive orphans` | 10.40 s, nothing found |
| `archive manifest status` | 0.45 s |
| `archive manifest verify --full`, one podcast | 0.46 s |
| `archive reconcile --deep` | 24.38 s |
| `archive reconcile --rebuild`, dry run over 100 000 sidecars | 25.44 s |
| `db check` | 2.77 s |
| `serve` until it answers | 0.53 s |
| `/archive`, every page of 500, 200 pages | median 5.75 ms, p95 6.69 ms |
| `/archive/invalid` | median 0.12 ms |
| `/archive/stats` | median 8.26 ms, p95 9.10 ms |

[`DATA_MODEL.md`](../DATA_MODEL.md) §7 plans for 500 000 archive files; 100 000 were measured. The archive's list and its pages do not grow with its size, while the passes over every file grow linearly: a light verification of 500 000 files would take about three minutes.

## Findings

| Found | Before | After | Change |
|---|---|---|---|
| A watcher that fell behind the event bus left completed downloads without an archive record until the next start | 452 of 1 000 downloads unrecorded in `serve` | all recorded once the bus is quiet | `74f87ba` |
| Every start stat'ed every archived file, for every command | 12.75 s until `serve` answered, 12.6 s for `archive manifest status`, 15.3 s for `db check` | 0.53 s, 0.45 s, 2.77 s | `8e0d989`, [ADR 0021](../DECISIONS/0021-archive-file-and-verification.md) amended |
| Every verification pass wrote one `archive.verified` per intact file: 100 000 events, about 46 MB, which pushed the rest of the history out of the 100 000-row event log | the database grew 46 MB per pass; `verify --all` 61 s | no growth; 36 s | `1f37a66`, ADR 0021 amended |
| `/podcasts?sort=episodes` counted every podcast's episodes for each page | 78.24 ms, p95 101.61 ms | 3.31 ms, p95 3.78 ms | `254731b`, migration 0009 |
| A search for a word in every episode ranks all 500 000 | 94 ms | unchanged | accepted, above |

The first refresh of 10 000 feeds took 119 s before migration 0009's trigger and 125 s after, within the run-to-run spread of this machine.

## Phase 3 and 4 benchmarks, run again

The criterion benches of Phases 2 to 4 ran at their own commits, `c033bbb` and `2bd5242` in the pre-publication history, and at `74f87ba`, both on this machine with rustc 1.98.1 and the settings of their reports. Medians:

| Benchmark | Then | Now | |
|---|---|---|---|
| `parse/10000` | 58.1 ms | 54.7 ms | −6 % |
| `normalize/10000` | 44.5 ms | 44.3 ms | 0 % |
| `identity/10000` | 30.6 ms | 31.8 ms | +4 %, between +4 % and +15 % over three runs |
| `refresh/identical_forced_full_parse/10000` | 193 ms | 188 ms | −3 % |
| `refresh/one_added_or_missing/10000` | 186 ms | 215 ms | +16 % |
| `refresh/one_updated/10000` | 180 ms | 215 ms | +19 % |
| `normalize 10k queries` (discovery) | 17.0 ms | 23.5 ms | **+38 %**, the same in three runs |
| `dedup+merge/100` | 8.44 ms | 9.85 ms | +17 % |
| `rank/1000` | 6.48 ms | 7.23 ms | +12 % |
| `token_set_ratio 1k pairs` | 841 µs | 844 µs | 0 % |
| `download_throughput/workers/8` | 53.2 ms | 44.8 ms | −16 % |
| `download_resume/finalize_only/100` | 52.3 ms | 51.2 ms | −2 % |
| `download_queue/enqueue/1000` | 535 ms | 491 ms | −8 % |

Parsing, normalizing and identity are where they were. A refresh that finds one changed item in 10 000 costs about 30 ms more, which a refresh of such a feed every interval can carry. Query normalization is 38 % slower, reproducibly: 2.3 µs instead of 1.7 µs per query, for the one query a search normalizes. Nothing here needs a change.

The benches that write files were not compared. On this machine one of them, `download_resume/resume_from_half`, measured 462 ms, then 915 ms and 112 ms, and the old commit measured 98 ms and then 111 ms. NTFS with real-time scanning spreads a bench that writes 32 MiB too far for a percentage to mean anything.

## Not measured

- Linux. Every number above is Windows on NTFS; a `stat` there costs more than on ext4.
- 500 000 archived files, and 10 000 podcasts with their files: the two tiers were measured apart.
- The web UI itself: these are the API requests it makes, not its rendering.
- A refresh against real hosts, where each feed is a TLS connection to a different server.
