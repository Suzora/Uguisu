# Benchmarks — Phase 2 discovery engine (2026-09-17)

Measured, not claimed. Numbers come from one criterion run on the development container; they are a baseline for regressions, not a performance guarantee.

## Setup

| Item | Value |
|---|---|
| Machine | 4 vCPU Intel Xeon @ 2.80 GHz (shared cloud container, no CPU pinning) |
| Toolchain | rustc 1.94.1, release profile, `cargo bench` |
| Criterion settings | `--warm-up-time 1 --measurement-time 3 --sample-size 20` |
| Benches | `crates/uguisu-discovery/benches/discovery.rs`, `crates/uguisu-http/benches/policy.rs` |
| Network | none; the search benches run against an in-process fake provider |

Reproduce with:

```bash
cargo bench --workspace -- --warm-up-time 1 --measurement-time 3 --sample-size 20
```

## Discovery pipeline (`uguisu-discovery`)

Times are the criterion point estimate with the 95 % confidence interval.

| Benchmark | What is measured | Time |
|---|---|---|
| `normalize 10k queries` | `NormalizedQuery::parse` on 10 000 mixed-script queries (NFKC, casefold, diacritics, tokens, URL detection) | 25.90 ms [25.84, 25.96] → ≈ 2.6 µs per query |
| `token_set_ratio 1k pairs` | `fuzzy::token_set_ratio` on 1 000 pre-folded title pairs | 1.50 ms [1.49, 1.52] → ≈ 1.5 µs per pair |
| `rank/100` | `rank::rank` over 100 candidates with a full `RankingExplanation` each | 1.23 ms [1.23, 1.24] |
| `rank/1000` | same, 1 000 candidates | 13.49 ms [13.15, 13.86] |
| `dedup+merge/100` | `dedup::group` + `merge::merge` for 100 candidates from 3 providers, every third sharing a feed URL | 14.88 ms [14.70, 15.10] |
| `dedup+merge/1000` | same, 1 000 candidates | 834.5 ms [830.0, 840.2] |
| `search 3 providers uncached (25 candidates each)` | `SearchEngine::search` with three in-process providers, cache disabled | 12.53 ms [12.28, 12.80] |
| `search 3 providers cached` | same request served from `DiscoveryCache` | 11.64 ms [11.56, 11.75] |
| `search 3 providers with 20ms latency each (parallel)` | each provider sleeps 20 ms; confirms fan-out is parallel (≈ 20 ms + pipeline, not 60 ms) | 33.87 ms [33.53, 34.27] |

## Network policy (`uguisu-http`)

| Benchmark | What is measured | Time |
|---|---|---|
| `classify_ip x7` | `classify_ip` on 7 addresses (public v4/v6, RFC 1918, link-local, IPv4-mapped loopback, 6to4) | 61.9 ns → ≈ 9 ns per address |
| `check_url x5` | `NetworkPolicy::check_url` on 5 URLs incl. literal loopback, allow-listed private host and rejected scheme | 478 ns → ≈ 96 ns per URL |

The pre-resolution policy check is negligible next to any network round trip.

## Reading the numbers

- **Dedup and merge scale quadratically** in the number of candidates because the title/author similarity pass compares every pair that shares no hard key. At the real-world size (three providers × ≤ 100 results = ≤ 300 candidates) this stays well under 100 ms; 1 000 candidates is a stress case, not a target. Blocking by first token or by a title n-gram index is the obvious optimization if larger fan-outs are ever configured (tracked in `docs/DISCOVERY.md` §13 and the roadmap).
- **The cached search is only ≈ 1 ms faster than the uncached one** because the fake providers respond in microseconds; the cost that remains is dedup + rank + JSON assembly for 75 candidates. Against real providers the cache saves the full network latency (hundreds of ms) plus provider quota.
- **Search overhead is dominated by dedup** (75 candidates → ≈ 10 ms). Ranking 75 candidates with explanations is ≈ 1 ms.
- **Parallel fan-out is confirmed**: three providers with 20 ms latency each finish in ≈ 34 ms, so the engine waits for the slowest provider, not for the sum.
- criterion warned that `normalize 10k queries` and `dedup+merge/100` could not complete 20 samples inside 3 s and extended the measurement window; the estimates are still from 20 samples.

## Not measured yet

- Live provider latency and the soft/hard deadline behaviour against Apple, Podcast Index and gpodder.net (Part B, needs network).
- Feed probe throughput on large real feeds (Phase 3 will measure the full parser instead).

## Re-run after Part B (same day, after the live-verification fixes)

The Part B corrections (Apple mapping, `cache_max_age` for `no-cache`, `moved_to` filtering) touch no hot path. A short re-run (`--warm-up-time 1 --measurement-time 3 --sample-size 20`, discovery search benches and the policy benches only) showed no regression: `check_url ×5` 326 ns, `classify_ip ×7` 60 ns, `search 3 providers uncached` 8.7 ms, `cached` 8.5 ms, `20 ms latency each` 30.2 ms. The lower numbers versus the morning run are within run-to-run noise on the shared container (the first run competed with a parallel build), not an improvement to claim.
