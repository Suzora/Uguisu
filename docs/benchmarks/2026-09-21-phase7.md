# Benchmarks — Phase 7 service, scheduler, settings and search (2026-09-21)

Measured, not claimed. The numbers come from two criterion runs on the development container. They are a baseline for regressions, not a performance guarantee. Nothing here touches a remote host.

Phase 7's cost is **per wake and per query**, not per byte. A scheduler pass asks three indexed questions and sleeps; a search reads one FTS index; a settings write is one row. The one expensive operation is building the search index, and it is paid once per library rather than once per start.

## Setup

| Item | Value |
|---|---|
| Machine | 4 vCPU Intel Xeon @ 2.80 GHz, 16 GB RAM (shared cloud container, no CPU pinning) |
| Toolchain | rustc 1.94.1, release profile, `cargo bench` |
| Criterion settings | defaults for the pure functions; `--warm-up-time 1 --measurement-time 3 --sample-size 20` for the settings group |
| Benches | `crates/uguisu-core/benches/schedule.rs`, `crates/uguisu-storage/benches/service.rs` |
| Storage | temporary SQLite databases on the container's overlay filesystem |

Reproduce with:

```bash
cargo bench -p uguisu-core    --bench schedule
cargo bench -p uguisu-storage --bench service -- --warm-up-time 1 --measurement-time 3 --sample-size 20
```

**How to read the database numbers.** Every timed closure acquires a connection from the pool and drives the query through `block_on`, because that is what a scheduler pass and an API request actually do. So roughly 100 µs of the figures below is pool acquisition and executor overhead rather than SQLite. That makes the *absolute* numbers pessimistic and the *shape* — how they change with the size of the library — the part worth reading.

## The scheduling arithmetic

Pure functions, run once per podcast per refresh.

| Operation | Time |
|---|---|
| `slot_permille` (a podcast's fixed share of the interval) | 5.6 ns [5.6, 5.6] |
| `plan_next`, ordinary | 34.7 ns [34.7, 34.8] |
| `plan_next`, catching up | 27.7 ns [27.3, 28.3] |

A thousand podcasts replanned after a week of downtime therefore cost about 35 µs of arithmetic in total. Whatever makes a restart slow, it is not the schedule.

## What a scheduler pass asks the database

The two queries a wake runs, against libraries of 0, 100 and 1 000 podcasts (half due, one in seventeen paused):

| Query | 0 podcasts | 100 | 1 000 |
|---|---|---|---|
| `due_ids` (both halves, 8 excluded ids, `LIMIT 8`) | 147 µs | 181 µs | 180 µs |
| `next_due_at` | 109 µs | 113 µs | 111 µs |

**Flat from 100 to 1 000**, which is the whole point of `idx_podcasts_due`: the query seeks and stops, so an idle daemon's cost does not grow with the library. The step from 0 to 100 is the difference between an empty index and one with rows to return, not a size effect.

An idle process wakes at most every fifteen minutes and runs both queries plus the pause read, so the steady-state cost of "Uguisu is running" is under a millisecond of database work per quarter-hour.

## Search

Libraries built by the triggers — no rebuild ran — and queried through `search_episodes` with a two-term query and a 25-row limit.

| Library | Two terms | Prefix (`async run*`) |
|---|---|---|
| 20 podcasts, 10 000 episodes | 4.55 ms [4.49, 4.62] | 4.52 ms [4.45, 4.60] |
| 100 podcasts, 100 000 episodes | 40.5 ms [40.0, 41.0] | 42.7 ms [42.3, 43.2] |

Linear in the size of the index rather than flat, because these benchmark queries match *everything*: the synthetic corpus repeats eight words across every title, so "async runtimes" matches a large fraction of the library and `bm25` has to rank it. A real query that matches a handful of episodes is far cheaper; a query that matches half the library is what this measures, and 40 ms for a hundred thousand episodes is the pessimistic end.

Prefix search costs the same, which is what `prefix = '2 3 4'` in the index definition buys.

### Building the index

| Library | Full rebuild (clear + batches of 1 000) |
|---|---|
| 10 000 episodes | 1.16 s [1.11, 1.23] |

≈ 8 600 episodes per second, so a 100 000-episode library takes roughly twelve seconds — which is exactly why the migration does not do it and `serve` does it in the background, in batches of a thousand with one transaction each, so the single writer stays available throughout. The 100 000-episode rebuild is not benchmarked: it is linear in rows, and a benchmark that takes ten seconds per iteration measures the harness's patience rather than the code.

## The query builder

What every search runs before any SQL does. Bounded by construction: at most sixteen terms of sixty-four characters.

| Input | Time |
|---|---|
| two words | 280 ns [278, 281] |
| seventeen words (one over the cap) | 2.41 µs [2.40, 2.41] |
| hostile (`"unterminated OR NEAR(x y) col:value ^anchor -negated ****`) | 1.39 µs [1.38, 1.40] |

Hostile input is *cheaper* than a long legitimate query, because most of it is discarded as punctuation. There is no input a user can type that makes the parser expensive.

## Settings

| Operation | Time |
|---|---|
| store one setting (`BEGIN IMMEDIATE`, upsert, commit) | 318 µs [316, 320] |
| read every stored setting | 104 µs [103, 106] |

A write is a committed transaction on the single writer, which is the 300 µs; a read is a pooled connection and one indexed scan of a table with tens of rows. Both are paid per API call, never per refresh or per download — the engine holds the merged configuration in memory and re-reads the table only when something changes it.

## What is not measured here

- **Start-up with a large database.** `Engine::open` runs migrations, reconciles the download queue and the archive, then reads the settings table. The Phase-4 and Phase-6 reports cover the reconciliation halves; Phase 7 adds one `SELECT` over a table with tens of rows.
- **The discovery cache's second tier.** A store read is a single-row primary-key lookup and a store write is one upsert; both are dominated by the same pool and transaction overhead as the settings numbers above, and neither is on a path a user waits for — a miss costs a provider call, which is three orders of magnitude slower.
- **A scheduler pass end to end.** It is dominated entirely by the refreshes it starts, which the Phase-3 report measured.
