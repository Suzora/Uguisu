# Benchmarks — Phase 5 archive engine (2026-09-19)

Measured, not claimed. Numbers come from one criterion run and one manual end-to-end run with the release binary on the development container; they are a baseline for regressions, not a performance guarantee. Nothing here touches the network or a remote host: the template work is pure computation, and the verification work reads a local file.

## Setup

| Item | Value |
|---|---|
| Machine | 4 vCPU Intel Xeon @ 2.10 GHz, 16 GB RAM (shared cloud container, no CPU pinning) |
| Toolchain | rustc 1.94.1, release profile, `cargo bench` |
| Criterion settings | `--warm-up-time 1 --measurement-time 3` (default sample size; 10 for the two heavy groups) |
| Bench | `crates/uguisu-archive/benches/archive.rs` |
| Storage | temporary directory on the container's overlay filesystem |
| Title under test | `Ep. 141: The Pizza Problem — Wie »Käse/Ketchup« das Büro sprengte (Teil 2/3)` — Unicode, punctuation, separators and length, so the sanitizer does real work rather than passing ASCII through |

Reproduce with:

```bash
cargo bench -p uguisu-archive --bench archive -- --warm-up-time 1 --measurement-time 3
UGUISU_TEST_LARGE=1 cargo bench -p uguisu-archive --bench archive -- verify   # adds the 1 GiB case
```

## Rendering a path

| Operation | Time |
|---|---|
| parse the default template | 842 ns [825, 860] |
| parse a template with filters and an optional group | 1.41 µs [1.40, 1.42] |
| render, `portable` | 3.62 µs [3.59, 3.64] |
| render, `windows` | 3.64 µs [3.61, 3.67] |
| render, `posix` | 3.15 µs [3.11, 3.18] |
| render with filters and an optional group | 3.01 µs [2.97, 3.04] |

`posix` is ~13 % faster because it has fewer characters to replace; the difference is the sanitizer, not the parser. Parsing is done once per configuration, not per episode.

**100 000 paths: 402 ms [391, 414] — 249 000 paths/s.** That figure includes building a fresh title and context per iteration, so it is a worst case: rendering an entire 100 k-episode library is well under a second of CPU. The roadmap asked for this number; the answer is that path rendering is not a cost worth optimizing further.

## Sanitizing a segment

| Operation | Time |
|---|---|
| segment, `portable` | 1.56 µs [1.54, 1.58] |
| segment, `windows` | 1.63 µs [1.58, 1.69] |
| segment, `posix` | 1.38 µs [1.36, 1.40] |
| segment, 400 characters truncated to 120 | 14.9 µs [14.7, 15.1] |
| file name with an extension and a collision suffix | 2.12 µs [2.10, 2.17] |

The 400-character case is ten times the typical one because NFC normalization and the character scan run over the whole input before truncation — the string has to be understood before it can be cut safely. It is still 15 µs, and it only happens for titles nobody writes on purpose.

## Choosing a path

| Operation | Time |
|---|---|
| collision: preferred path free | 22.3 ns [21.8, 22.8] |
| collision: preferred taken, suffix applied | 1.37 µs [1.36, 1.39] |
| the stable suffix itself | 138 ns [136, 139] |
| parse a stored relative path | 90.9 ns [90.1, 91.7] |
| join onto the root | 376 ns [371, 380] |
| component-wise containment check | 205 ns [201, 209] |
| symlink-aware resolution (`resolve_checked`) | 4.85 µs [4.79, 4.90] |

The free case is a hash lookup. The taken case costs a re-sanitized file name, which is the 1.37 µs. `resolve_checked` is ~24× the plain join because it canonicalizes the deepest existing ancestor — one or more `readlink`/`stat` syscalls. That is the price of proving a symlink cannot lead out of the archive, and it is paid once per file operation, never per byte.

## Verifying an artifact

100 MiB file, and 1 GiB behind `UGUISU_TEST_LARGE`:

| Depth | 100 MiB | 1 GiB |
|---|---|---|
| `existence` | 3.46 µs | 3.46 µs |
| `light` | 3.67 µs | 3.40 µs |
| `full` | 89.7 ms — **1.09 GiB/s** | 888 ms — **1.13 GiB/s** |

The shallow depths are flat in file size because they never read the file: one `symlink_metadata`, then a comparison. That is the whole point of the three depths, and it is why startup reconciliation stats instead of hashing — checking a 10 000-file archive for missing files costs about 35 ms of syscalls, while hashing it would cost as many seconds as it has gigabytes.

`full` is bounded by SHA-256, not by I/O: the same ~1.1 GiB/s at 100 MiB and at 1 GiB, with a 1 MiB buffer, so memory use does not grow with the file. The benchmark declares a byte throughput only for `full`; declaring one for the shallow passes would divide the file size by a time that never touched the bytes and report tens of TiB/s, which would be impressive and untrue.

## Deciding a policy

| Operation | Time |
|---|---|
| `decide` → queue | 14.8 ns [14.8, 14.9] |
| `decide` → skip (disabled) | 19.6 ns [19.4, 19.8] |

A pure function over a struct. Evaluating a policy for a whole 10 000-episode feed is ~150 µs; the cost of automatic archiving is entirely in the queue and the transfer, never in the decision.

## End to end with the release binary

`target/release/uguisu` against a local HTTP host serving a three-item feed with 8 MiB enclosures (`docs/benchmarks/` script, temporary data directory):

| Step | Result |
|---|---|
| add podcast and ingest 3 episodes | 1.70 s (dominated by resolution and the first fetch) |
| download 24 MiB | 0.10 s — 237 MiB/s |
| resulting layout | `Darknet Diaries/2024/2024-01-15 - Episode 0- Käse & Ketchup - Teil 0.mp3` |
| bytes identical to the source | yes, SHA-256 per file |
| `archive verify --all` (light) | 18 ms, 3 verified |
| `archive verify --all --full` | 43 ms, 3 verified — 563 MiB/s including process start and engine open |
| `archive relocate --all --dry-run` | 18 ms, 0 moves (already on the template path) |
| database | 260 KiB for 3 episodes |

The layout line is the point of the phase: the Unicode survives, the `/` inside the title became `-` rather than a directory, and the name is one a person can read.

Then one file was tampered with (one byte flipped, length preserved) and another deleted:

| Assertion | Result |
|---|---|
| `verify --all --full` exit code | 1 |
| what it reported | 1 verified, 1 invalid, 1 missing — exactly the injected faults |
| the tampered file after verification | byte-for-byte as the test left it |
| the deleted file after verification | still absent; nothing re-created it |
| `archive missing` / `archive invalid` | 1 each |
| the invalid file's record | kept, with the **download's** hash, not the tampered file's |
| after a full restart | still 1 missing, 1 invalid — a startup pass cannot clear a finding |

That last row is the one worth keeping: a shallow existence check at startup sees the tampered file present and must not conclude anything from that. It reports `present` and writes nothing.

## What is not measured here

- **A 100 k-file scan against a real archive.** `verify_all` pages in batches of 200 and its per-file cost is the table above; what a 100 k scan adds is SQLite paging, which the Phase-3 benchmarks already cover and which the Phase-8 report will measure end to end.
- **Windows.** The `windows` profile is measured; the actual filesystem behaviour it defends against (reserved names, sharing violations, no directory fsync) is not, because CI has no Windows runner yet. This is the open half of R6.
- **Relocation throughput.** A relocation is one `rename` plus one row update; the interesting number would be the filesystem's, not Uguisu's.
