# Benchmarks — Phase 4 download engine (2026-09-18)

Measured, not claimed. Numbers come from one criterion run and one manual measurement on the development container; they are a baseline for regressions, not a performance guarantee. Every transfer is on loopback, so these measure the engine — streaming, hashing, progress writes, finalization, queue admission — and never an internet connection.

## Setup

| Item | Value |
|---|---|
| Machine | 4 vCPU Intel Xeon @ 2.10 GHz, 16 GB RAM (shared cloud container, no CPU pinning) |
| Toolchain | rustc 1.94.1, release profile, `cargo bench` |
| Criterion settings | `--warm-up-time 1 --measurement-time 5 --sample-size 10` |
| Bench | `crates/uguisu-download/benches/downloads.rs` |
| Network | none; bodies come from the in-process scenario media server (`uguisu-download/testing`) on 127.0.0.1 |
| Storage | temporary directory on the container's overlay filesystem, SQLite WAL, `synchronous=NORMAL` (ADR 0002) |
| Settings | `max_attempts = 1`, `progress_interval = 1 s`, `min_free_bytes = 0`; body generation is deterministic per size |

Reproduce with:

```bash
cargo bench -p uguisu-download --bench downloads -- --warm-up-time 1 --measurement-time 5 --sample-size 10
```

## Throughput and worker scaling

A fixed payload of 32 MiB per iteration, split evenly across the workers under test (1 × 32 MiB, 4 × 8 MiB, 8 × 4 MiB), each job queued fresh and run end to end through the scheduler: claim, stream, hash, finalize, persist.

| Workers | Time for 32 MiB | Throughput |
|---|---|---|
| 1 | 75.3 ms [74.3, 76.2] | 425 MiB/s [420, 431] |
| 4 | 51.4 ms [50.1, 53.1] | 622 MiB/s [602, 639] |
| 8 | 49.0 ms [48.1, 49.7] | 653 MiB/s [644, 666] |

Four workers are 1.46 × one worker, eight are 1.54 ×. A single job already saturates a large part of the loopback path, and the remaining scaling is limited by the four vCPUs shared between the media server, the HTTP client, SHA-256 and the filesystem. On a real connection the per-host limit (default 1) and the remote host are the binding constraints, not this ceiling.

## Resume and finalization

One job at a time through the real worker, 32 MiB unless stated. "Fresh" transfers the whole body; "resume from half" starts with 16 MiB already in the `.part` file and valid validators, so the worker re-hashes the prefix and asks for `Range: bytes=16777216-`; "finalize only" starts with the complete file on disk, so there is no transfer at all — it is the cost of re-hashing, `fsync` and the rename.

| Benchmark | Time | Bytes accounted | Rate |
|---|---|---|---|
| `fresh_32MiB` | 67.0 ms [62.8, 72.1] | 32 MiB transferred | 478 MiB/s |
| `resume_from_half` | 60.3 ms [58.9, 62.3] | 16 MiB transferred (+ 16 MiB re-hashed) | 265 MiB/s of new data |
| `finalize_only` 32 MiB | 33.8 ms [32.3, 35.6] | 32 MiB re-hashed | 948 MiB/s |
| `finalize_only` 100 MiB | 92.6 ms [92.0, 93.1] | 100 MiB re-hashed | 1.05 GiB/s |

Reading and hashing an existing `.part` costs about 1 GiB/s, so resuming a half-finished 32 MiB file costs roughly as much as transferring it fresh: the saved transfer (16 MiB) is paid back as a re-hash (16 MiB) plus the rename. That trade is deliberate (ADR 0019): hashing is cheap and local, bandwidth is not, and it also proves the prefix is readable before the transfer continues. On a real connection, where 16 MiB takes seconds rather than 35 ms, resuming is a large win.

Finalization of a 100 MiB file — hash, `sync_all`, rename, directory fsync, one transaction — is 93 ms, of which the hash is most.

## Queue

| Benchmark | Time | Per item |
|---|---|---|
| `enqueue` 100 episodes | 68.0 ms [67.7, 68.6] | 680 µs |
| `enqueue` 1 000 episodes | 746 ms [721, 775] | 746 µs |
| `first_claim_of` 1 000 queued jobs | 1.57 ms [1.47, 1.67] | — |

Enqueue is linear at ≈ 0.7 ms per episode: each one is its own transaction (load the episode, check for a duplicate job, insert, write the `download.queued` event) on a WAL database with `synchronous=NORMAL`. Queueing a 1 000-episode back catalogue therefore costs under a second; the bulk path (`download podcast`) pays the same per row.

With a 1 000-job queue, the time from `start()` to the first `download.started` is 1.6 ms: the claim query is a single indexed lookup (`state, priority DESC, created_at, id`) and does not scan the queue.

## The release binary on a 512 MiB download

Manual run of `target/release/uguisu` against `python3 -m http.server` serving a generated 512 MiB file (SHA-256 known in advance); peak resident set size and CPU time from `getrusage(RUSAGE_CHILDREN)`.

| Measurement | Value |
|---|---|
| Command | `uguisu --json download <episode-id> --wait` |
| Wall time | 2.87 s (178 MiB/s) |
| Reported `duration_ms` | 2 852 |
| CPU | 0.55 s user, 2.40 s system |
| Peak RSS | 17.9 MiB |
| Result | `completed` in one attempt; stored hash equals the generator's SHA-256 |

Memory does not scale with the file: the body is streamed through a 256 KiB buffered writer and hashed as it goes. The test suite checks the same property automatically — `crates/uguisu-download/tests/large.rs` downloads 1, 10 and 100 MiB (and 1 GiB with `UGUISU_TEST_LARGE=1`) and fails if the process's peak RSS grows more than 64 MiB above its baseline. The 1 GiB run: 27.7 s, +20 MiB peak RSS.

System time dominates because every byte is written through `tokio::fs` (a blocking write on the runtime's pool) and the file is `fsync`ed before the rename.

## What this says about the defaults

- `UGUISU_DOWNLOAD_GLOBAL_CONCURRENCY = 3` with `PER_HOST_CONCURRENCY = 1` is a politeness setting, not a throughput limit: one worker alone can absorb far more than a typical podcast host serves.
- `progress_interval = 1 s` means at most one small `UPDATE` and one bus event per second per job, which is invisible next to the transfer.
- The single SQLite writer is not a bottleneck for downloads: the write set per job is a handful of rows, and the only per-byte cost is the hash.

## Regressions to watch

- Throughput at one worker dropping below ≈ 300 MiB/s would suggest an extra copy or a lost buffer in the body loop.
- `finalize_only` moving far from the hash rate (≈ 1 GiB/s) would mean finalization gained I/O it should not have.
- `first_claim_of` growing with queue size would mean the claim query stopped using its index.
